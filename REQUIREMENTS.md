# Rust SEP Winter Term 25/26 – Final Project

## Requirements
**Requirements written in bold are mandatory but not sufficient to pass.**  
Other requirements should be fulfilled for a 1.0, but are also not sufficient.

---

## Git
- [ ] **(G1) The submitted project is a Git repository.**
- [ ] **(G2) The main branch contains the final project.**
- [ ] **(G3) Collaborative development was continuously done via Git (commit history from December to February).**
- [ ] **(G4) Use of feature branches and pull requests with reviews by another teammate.**
- [ ] **(G5) Everyone committed Rust code in an amount corresponding to their skill level.**
- [ ] (G6) There are at least two server‑side quality gates for pull requests configured, latest one month after the first commit.  
- [ ] (G7) Git commits on the main branch have descriptive commit messages.  
- [ ] (G8) Git commits on the main branch are compilable.  
- [ ] (G9) Git commits on the main branch are atomic.  
- [ ] (G10) The history on the main branch is linear.

---

## Code
- [ ] **(C1) The project must be compilable with rustc stable 1.85.0 (edition=2024).** 
- [ ] **(C2) The project is executable.**
- If the project is runnable via `cargo run`, it’s fine.  
- If depending on non–crates.io dependencies, a devcontainer must include all required components.  
- If depending on external services, test credentials must be provided.  
- If extra hardware is required, include a simulator or borrow the hardware from the deadline to oral exam.

- [ ] (C3) There are no compiler warnings.  
- [ ] (C4) The code is properly formatted according to the configured style.  
- [ ] (C5) There are no clippy warnings.  
- [ ] (C6) Each `unsafe` usage has a comment explaining why it was necessary.  
- [ ] (C7) User input is handled gracefully.  
- [ ] (C8) The code is tested with a sensible testing method.  
- [ ] (C9) Non‑obvious functionality is documented with comments.  
- [ ] (C10) The code is sensibly structured using modules.
